# HLK-LD2450 — 24 GHz Multi-Target mmWave Radar (reference)

Sources: `006000_HLK-LD2450-Instruction-Manual.pdf` (hardware, v1.00) and `LD2450 serial
port communication protocol V1.03.pdf` (protocol) under
`docs/datasheets/externalDevices/LD2450 HiLink 24GHz_Multitarget_mmWave_Sensor/`.
Ground truth for what's actually wired/working: `main/prop_motion.c` (UART2, GPIO53/54,
256000 baud). The config-command protocol below (mode/BT/zone/version/MAC/restart/baud
read-write) is **implemented** as the `prop_motion_cfg_*` API in `main/prop_motion.c` /
`main/include/prop_motion.h`, exposed over HTTP as `GET /ld2450` + `POST /cmd`
`{"cmd":"ld2450",...}` (see `tools/prop.py ld2450`). Implemented from
`docs/superpowers/plans/2026-07-01-sensor-protocol-followups.md`.

The two hardware-manual PDFs in that folder are identical content (one has FCC boilerplate
appended) — treat as one source. The protocol PDF is the only source for the config-command
frame format below, which isn't reflected anywhere else in the repo.

## The folder's README.md was wrong — now replaced

It used to describe a *different* sensor's feature set entirely: GP1/GP2 digital presence
pins, a 6–8 pin "expansion header," 115200 baud, "Upper Computer" sensitivity Levels 1-3,
Area/Small-Area detection scene modes. **None of that exists on the LD2450.** The real
module has 4 pins (5V/GND/TX/RX), default baud 256000, and streams structured 3-target
Cartesian tracking frames — a fundamentally different protocol from GPIO-level presence
detection. That content was actually the **MR24HPC1**'s real spec sheet, copy-pasted into
the wrong folder (see `references/mr24hpc1.md` — its README was byte-identical to this one).

## Data frame protocol (the part firmware implements — read-only parsing)

10 Hz, 30-byte fixed-length frames, little-endian:

`AA FF 03 00` (header, 4B) · Target1 (8B) · Target2 (8B) · Target3 (8B) · `55 CC` (tail, 2B)

Per-target 8-byte layout — **all 3 slots always present**, even for absent targets (fixed
slots, not a variable-count list; an inactive slot is all-zero X/Y):

| Field | Type | Bytes | Unit | Notes |
|---|---|---|---|---|
| X | sign-magnitude int16 | 0–1 | mm | bit15=sign (1=+), bits0–14=magnitude |
| Y | sign-magnitude int16 | 2–3 | mm | same encoding |
| Speed | sign-magnitude int16 | 4–5 | **cm/s** | same encoding — raw unit is cm/s, not mm/s |
| Distance resolution | uint16 | 6–7 | mm | size of the distance gate the target was in |

**Sign-magnitude, not two's complement** — confirmed in both PDFs and in `prop_motion.c`'s
decode. Treating it as plain int16 corrupts positive values (e.g. raw `0x8391` = +913mm
decodes as a large negative number under two's-complement). `prop_motion.c` treats a slot as
active only when `x != 0 || y != 0`, matching the datasheet's all-zero example for absent
targets. See also the `ld2450-sign-magnitude` project memory.

**Unit gotcha:** speed is **cm/s** in the raw frame; double-check any downstream field/name
implying mm/s actually accounts for the ×10 if precise speed ever matters.

## Config-command protocol

Separate frame envelope from the data-output frames, same UART, bidirectional command/ACK:

`FD FC FB FA` (header, 4B) · length (2B LE) · command word (2B) + value (N bytes) · `04 03 02 01` (tail, 4B)

ACK frames use the identical envelope; the echoed command word has bit8 set
(`sent_word | 0x0100`), followed by a 2-byte status (`0000`=success, `0001`=failure), then any
return payload. All multi-byte fields are little-endian **except the MAC address** (see below).

**Sequencing is mandatory:** send "Enable Config" (`0x00FF`, value `0x0001`) before any other
command, and "End Config" (`0x00FE`) afterward to resume normal data streaming. Commands sent
outside that bracket are invalid/ignored. Every byte layout below was checked against the
protocol PDF's own worked examples (not just the command-table prose):

| Command | Word | Value (send) | ACK payload (after status) | Notes |
|---|---|---|---|---|
| Enable configuration | 0x00FF | `01 00` | protocol version (2B) + buffer size (2B) | e.g. version `01 00`, buffer `40 00` |
| End configuration | 0x00FE | none | none | Resumes normal streaming |
| Single-target tracking | 0x0080 | none | none | |
| Multi-target tracking | 0x0090 | none | none | **Factory default** |
| Query tracking mode | 0x0091 | none | mode (2B): `0001`=single, `0002`=multi | |
| Read firmware version | 0x00A0 | none | fw type (2B, `0000`) + major (2B) + minor (4B) | see decode below |
| Set baud rate | 0x00A1 | 2B index (below) | none | Persists; needs reboot (`0x00A3`) to take effect |
| Restore factory defaults | 0x00A2 | none | none | Needs reboot to take effect |
| Restart module | 0x00A3 | none | none | Module auto-reboots right after sending this ACK |
| Bluetooth on/off | 0x00A4 | `0100`=on, `0000`=off | none | **ON by default**; persists, needs reboot |
| Get MAC address | 0x00A5 | `01 00` | MAC (6B, **big-endian**, no prefix byte) | Onboard BT radio's MAC. The PDF documents type(1B)+MAC(3B) but real fw V2.04 hardware returns a plain 6-byte MAC (bench-verified). With BT off it reports the placeholder `08:05:04:03:02:01`, not its real MAC |
| Query zone filter | 0x00C1 | none | filter type (2B) + 3× zone (8B each = 24B) | see zone format below |
| Set zone filter | 0x00C2 | filter type (2B) + 3× zone (8B each = 26B total) | none | Persists immediately, no reboot |

Baud index table (for `0x00A1`): `0x0001`=9600, `0x0002`=19200, `0x0003`=38400, `0x0004`=57600,
`0x0005`=115200, `0x0006`=230400, **`0x0007`=256000 (factory default)**, `0x0008`=460800.

**Factory defaults** (what `0x00A2` restores, confirmed from the PDF's table): baud 256000,
Bluetooth **on**, tracking mode **multi-target**, zone filtering **off**.

**Zone filtering** (`0x00C1`/`0x00C2`): filter type `0`=disabled, `1`=detect-only-inside,
`2`=exclude-inside. Each of the 3 zones is 4× `int16` (x1,y1,x2,y2 — diagonal rectangle
corners, mm) — confirmed **plain signed int16 (two's complement)**, e.g. `18 FC` LE = `0xFC18`
= -1000. **This is different from the sign-magnitude encoding the real-time data frames use** —
getting that backwards silently corrupts every negative zone coordinate. All-zero coordinates on
a zone slot mean that slot is unused.

**Firmware version decode**: the worked example `00 00 02 01 16 24 06 22` (fw type, major×2,
minor×4) prints as `V1.02.22062416`. The transform: major = byte[1]:byte[0] displayed as
`V{byte[1]}.{byte[0]:02X}`; minor = the 4 bytes displayed **reversed and as hex pairs**,
`{byte[3]:02X}{byte[2]:02X}{byte[1]:02X}{byte[0]:02X}`. Inferred from one example — trust the raw
bytes over this pretty-print if it ever looks wrong on a real module.

**Implemented in this project's firmware** (2026-07-01): `prop_motion_cfg_*` in
`main/prop_motion.c` / `main/include/prop_motion.h` — get/set tracking mode, zone filter,
restart, factory-reset, baud rate (with restart+resync fallback); get for firmware version and
MAC; set-only for Bluetooth (no status-query command exists in the protocol; the firmware turns
BT off at boot). Exposed over HTTP: `GET /ld2450` (aggregate read) and `POST /cmd`
`{"cmd":"ld2450","action":...}` writes, wrapped by `tools/prop.py ld2450`. Concurrency design:
motion_task is the sole UART reader and routes config-ACK frames to whichever caller is waiting,
alongside its existing data-frame parsing — the two frame types have distinct headers so there's
no ambiguity.

## Gotchas / nuances

- **Bluetooth is on by default** on the module's own onboard BT (separate from the P4/C6
  radios) — pairs directly with Hi-Link's phone/PC config app. Turn off via `0x00A4` if BT
  coexistence with the C6's BLE stack (`prop_ble.c`) is ever suspected as an interference source.
- Baud-rate and factory-reset changes need a module reboot (`0x00A3`); zone-filter changes take
  effect immediately.
- **Frame resync**: firmware already handles corrupt/partial frames by rescanning for the
  4-byte header, discarding a byte at a time on tail mismatch — consistent with the datasheet
  giving no CRC/checksum, only fixed header/tail sequences.
- The firmware UI's `FAN_HALF_DEG` (50°) intentionally renders *narrower* than the real ±60°
  FOV for cosmetic full-page fan rendering — that's a display choice, not a sensor limit.
- Wall-mount height 1.5–2 m recommended; radome must be non-metallic (metal blocks 24 GHz
  entirely). Avoid mounting multiple 24 GHz radars facing each other directly.
- The vendor PC "Upper Computer" tool speaks this exact same 256000-baud protocol — useful for
  isolating a hardware/firmware bug by plugging the module into a USB-serial adapter directly.
