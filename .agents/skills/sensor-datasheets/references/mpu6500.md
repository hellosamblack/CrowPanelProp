# MPU-6500 Accelerometer/Gyro — Datasheet Reference

Chip on this board: soldered part reports **WHO_AM_I = 0x70** → genuinely MPU-6500, not
MPU-6050 (WHO_AM_I 0x68). Load-bearing fact (see the `imu-is-mpu6500` project memory): the
MPU-6050 DMP firmware blob is incompatible with MPU-6500 silicon, which is why this repo
vendors LibDriver's dedicated `mpu6500` eMD core (`components/mpu6500/`) instead of a generic
MPU-6050 lib. Confirmed against `mpu6500_register_map.pdf` (Register 117/0x75 WHO_AM_I).

mechanics, ADC/FS-range constants, and address-bit encoding** (identical across the family —

## 2. PS-MPU-6000A doc: what carries over to MPU-6500, what doesn't

Same physical family (24-pin 3×3×0.9mm QFN, mostly same pin numbers), so a lot of the
mechanical/protocol-layer content is safe to reuse — but the pinout table has one actively
wrong row for MPU-6500:

| Topic | PS-MPU-6000A / old README says | MPU-6500 reality | Verdict |
|---|---|---|---|
| Pin 8 | "VLOGIC, MPU-6050 only... Digital I/O supply voltage" (implies MPU-6000 uses it as `/CS`) | Pin 8 is **VDDIO** — MPU-6500 *does* have a separate digital-IO supply pin (renamed VLOGIC→VDDIO), populated the same way. MPU-6500 has no QFN `/CS` pin in this position at all; SPI chip select is pin 22 (`nCS`) | **Misleading as written** — don't reuse this row verbatim |
| Pin 22 | Not in the 6000/6050 table shown | `nCS`, chip-select, SPI mode only | Old README's table is incomplete for MPU-6500; use product-spec Table 10 instead |
| VDD range | 2.375–3.46V | **1.71–3.45V** (VDD and VDDIO both) — notably wider/lower floor | **Different** — don't reuse the 6000/6050 voltage row |
| REGOUT/CPOUT caps | 0.1µF REGOUT, 2.2nF CPOUT | 0.1µF VDD bypass, 10nF VDDIO bypass, 0.1µF REGOUT — **no CPOUT pin/cap on MPU-6500** (charge pump is 6000/6050-only) | **6000/6050-specific, doesn't apply** |
| I²C address bits | `1101000`/`1101001` (AD0 low/high) | Same: 0x68/0x69 | Safe |
| I²C bus speed | up to 400kHz Fast / 100kHz Standard | 400kHz Fast Mode | Safe |
| I²C protocol framing | START/ACK single/burst read-write | Identical across the family | Safe |
| ADC word length / two's complement | 16-bit two's complement | Same | Safe |
| Gyro/accel FS ranges + sensitivity | ±250/500/1000/2000°/s, ±2/4/8/16g, 131 LSB/(°/s), 16384 LSB/g | Same values/encoding | Safe |
| Operating temp | -40 to +85°C | Same specified range (absolute max -40 to +105/125°C) | Safe |
| Package | 24-pin QFN 3×3×0.9mm | Same | Safe |

On this board, VDD and VDDIO are almost certainly tied together (typical single-rail 3.3V
design), so the VLOGIC/VDDIO distinction is probably moot in practice — but if debugging a
power/pinout issue, check the MPU-6500-specific pinout table, not the old local README.

## 3. I2C address / bus — confirmed against firmware

| Fact | Value | Source |
|---|---|---|
| 7-bit I2C address | **0x68** (AD0 low) or 0x69 (AD0 high) | `prop_imu_iic.c` (`IMU_I2C_ADDR 0x68`); `prop_imu.c` calls `mpu6500_set_addr_pin(..., MPU6500_ADDRESS_AD0_LOW)` |
| WHO_AM_I | **0x70** for MPU-6500 vs 0x68 for MPU-6050 | Register map, Register 117 (0x75) |
| Bus speed | 400 kHz Fast Mode; MPU-6500 has no faster register-read mode (that's MPU-6000 SPI-only, 20MHz burst — not applicable, this board is I2C-only) | Product spec §4.9 |
| Bus sharing | Shared `bsp_i2c` bus (I2C_NUM_0, GPIO45/46) with GT911 touch at 0x14/0x5D — no address conflict | See the `board-io` skill for the full bus map (not duplicated here) |

The AD0 address-select mechanism, address encoding, and bus speed are identical across
MPU-6000/6050/6500 — safe to reuse from the old doc. WHO_AM_I *value* is the one hard
divergence, and it's the fact `prop_imu`'s whole chip-identification design pivots on.

## 4. DMP capabilities: official spec vs LibDriver-added

The **official** MPU-6500 product spec (§4.8) lists a narrow DMP feature set: Low Power
Quaternion (**3-axis gyro-only**, not 6-axis fused), Screen Orientation, Pedometer. DMP runs
internally at ~200Hz regardless of host read rate; results land in a 512-byte FIFO with one
interrupt pin. Neither PDF mentions **tap detection**, **6-axis (accel+gyro) quaternion**, or
**gyro auto-calibration** anywhere — those register-map sections only cover DMP_EN/FIFO_EN/
DMP_RST control bits; the algorithm content itself is an opaque firmware blob.

This firmware (`main/prop_imu.c`) actively uses several DMP features that are **LibDriver/eMD
software-stack additions on top of the InvenSense DMP blob**, documented only in the LibDriver
README/`driver_mpu6500.h`, not in either InvenSense PDF:

| Feature used in `prop_imu.c` | In official MPU-6500 PDFs? | Actually documented in |
|---|---|---|
| `MPU6500_DMP_FEATURE_6X_QUAT` (quaternion → pitch/roll/yaw) | No (only 3-axis gyro-only quat is official) | LibDriver header/README dmp example |
| `MPU6500_DMP_FEATURE_TAP` + tap axis/direction/count | No | LibDriver README (`a_dmp_tap_callback`, `MPU6500_DMP_TAP_*`) |
| `MPU6500_DMP_FEATURE_PEDOMETER` + step count | Yes (officially listed) | Both — LibDriver exposes the getter |
| `MPU6500_DMP_FEATURE_ORIENT` (screen orientation) | Yes | Both |
| `MPU6500_DMP_FEATURE_GYRO_CAL` (gyro auto-cal) | No | LibDriver-only; per `prop_imu.c` comments, in practice **insufficient alone** — firmware layers its own continuous rest-triggered re-zero on top because DMP's GYRO_CAL + one-shot self-test bias don't fully null yaw drift on this unit |
| `mpu6500_self_test()` → accel/gyro offset | Not part of the DMP feature list (core-chip self-test, register-level) | Register map covers self-test registers generically; LibDriver wraps it |

**Practical implication:** for *what a DMP feature constant does or how to call it*, go to the
LibDriver README/header — it's the only place documenting the actual C API (callback
signatures, tap direction enums, `mpu6500_dmp_set_feature` flag combos). The InvenSense PDFs
confirm a feature is *real silicon behavior* (pedometer, orientation) or *raw register
semantics* (FIFO enable bits, WHO_AM_I, self-test registers) — they won't explain the 6-axis
quaternion/tap API surface at all, since that's eMD/LibDriver architecture on top of a vendor
firmware blob (`mpu6500_dmp_load_firmware()`).

## 5. Firmware-observed gotchas not in any datasheet

- **Accel self-test fails on this specific unit** — firmware has a fallback that measures its
  own zero-rate gyro bias at boot (assumes board stationary) when `mpu6500_self_test()`
  doesn't produce a usable offset. Per-unit empirical workaround, not a datasheet fact.
- **Zero-length FIFO reads must return success, not error** — LibDriver's `dmp_read` issues
  0-length reads when less than one packet is buffered; ESP-IDF's new I2C master driver
  rejects 0-length transfers, so the link layer short-circuits `len==0` to "OK". An ESP-IDF/
  LibDriver interface mismatch, not chip behavior.
- **Non-NULL SPI link functions required even in pure I2C mode** — `prop_imu.c` installs
  harmless SPI stubs purely to satisfy `DRIVER_MPU6500_LINK_SPI_*` macros; this board never
  uses SPI to the IMU (I2C-only wiring, no `nCS`/SPI lines routed).
- **No INT pin wired** — `prop_imu_task` polls the DMP FIFO every 40ms rather than using the
  DMP/FIFO-overflow interrupt the chip supports; the MPU-6500 `INT` pin isn't connected to any
  ESP32-P4 GPIO on this board (board-wiring choice, not a chip limitation).
- **Quaternion output is Q30 fixed-point** — `prop_imu.c` divides raw `quat[0..3]` by
  1073741824.0f (2^30) to get float. This scaling convention comes from the InvenSense eMD/DMP
  firmware output format; not stated in either PDF (register map only documents raw-sensor FIFO
  byte layout, not DMP quaternion packet encoding).

## 6. Bottom line

Treat the old local `README.md` (PS-MPU-6000A-sourced) as useful only for generic I2C
protocol mechanics, FS-range constants, and address-bit encoding. For anything electrical
(voltage rails, absolute max ratings, bypass caps) or DMP-feature-specific, go straight to
`libdriver mpu6500/datasheet/mpu6500_product_specification.pdf` and `mpu6500_register_map.pdf`
— the only MPU-6500-titled, MPU-6500-verified sources in this folder. For the actual C API
surface, `libdriver mpu6500/README.md` / `driver_mpu6500.h` is authoritative and the
InvenSense PDFs won't help at all.
