# DFRobot SEN0395 — 24 GHz mmWave Presence Sensor (reference)

Sources: `SEN0395 Datasheet.pdf`, `DFRobot_mmWave_Radar.h`/`.ino` (vendor Arduino library)
under `docs/datasheets/externalDevices/SEN0395 DFRobot 24GHz_mmWave_Sensor/`. Ground truth for
what's wired/working: `main/prop_aux_radar.c` (UART1, GPIO33/34, J10).

**This folder's README.md is accurate** — unlike the LD2450/MR24HPC1 sibling READMEs (see
those reference files), every checkable claim here matches the real PDF and vendor `.h`/`.ino`.
Minor gaps below are additions, not corrections.

## 1. Electrical / RF specs (confirmed against PDF)

| Parameter | Value |
|---|---|
| Operating voltage | 3.6–5V |
| Operating current | 90 mA |
| Modulation | FMCW + CW multi-mode |
| Operating frequency | 24 GHz |
| Equivalent transmit power | 13–15 dBm |
| Detection distance | 9 m |
| Beam angle | 100° × 40° |
| Operating temperature | -40 to 85°C |
| Baud rate | 115200, 8N1, no flow control |
| Dimensions | 24×28 mm |

Pinout (8-pin header): UART Tx, UART Rx, GPIO1 (general I/O), GPIO2 (presence output — high on
detect, default), GND, VCC, NC, NC. GPIO2 alone can act as a level-triggered switch without
touching UART at all — unused on this board (UART only).

## 2. Command protocol — core rules

- ASCII string commands, **ending in newline**, space-separated tokens.
- **CRITICAL RULE** (verbatim from the PDF): sensor **must be halted (`sensorStop`) before
  changing any working parameter**; after reconfiguring, **`saveCfg ...` must be sent to
  persist to flash** — otherwise changes are lost on power cycle.
- **Not in the PDF, only in the vendor `.h`:** commands must be spaced **≥1000 ms apart**
  (`#define DELAY 1000` in `DFRobot_mmWave_Radar.h`) — the sensor's CLI can't keep up with
  back-to-back writes. The README doesn't mention this; it's the one gap worth knowing.

## 3. Command reference

| Command | Syntax | Notes |
|---|---|---|
| Stop | `sensorStop` | Halts sensor; required before any cfg change |
| Start | `sensorStart` | Resumes running |
| Detection range | `detRangeCfg par1 parA_s parA_e [parB_s parB_e [parC_s parC_e [parD_s parD_e]]]` | `par1` hardcoded `-1`. Up to 4 disjoint segments, indices 0–127, each unit = **15cm**. Segments must be strictly ascending/non-overlapping. Example (1.5–3.0m): `detRangeCfg -1 10 20`. **Default: `detRangeCfg -1 0 20`** (0–3m) |
| Output latency | `outputLatency par1 par2 par3` | `par1` hardcoded `-1`. `par2`=entry/detect confirmation delay, `par3`=disappearance/clear confirmation delay. Range 0–65535, unit = **25ms** each. **Default: par2=100 (2.5s), par3=400 (10s)** |
| Startup mode | `sensorCfgStart par1` | `0` = wait for explicit `sensorStart` (**this is the real default** per the PDF's parameter description, despite one example table row mislabeling `1` as default); `1` = auto-run on boot |
| Save config | `saveCfg 0x45670123 0xCDEF89AB 0x956128C6 0xDF54AC89` | Fixed/hardcoded magic values (an interlock, not real config data). Fails if nothing changed |
| Factory reset | `factoryReset 0x45670123 0xCDEF89AB 0x956128C6 0xDF54AC89` | Same magic values |
| System reset | `resetSystem` | No response on success (reboots immediately); `Error` string only on failure |

## 4. Output frame protocol

`$JYBSS,par1,par2,par3,par4*` — starts `$`, comma-separated, ends `*`. Emitted at **1 Hz** default.

| Field | Meaning |
|---|---|
| par1 | `0` = clear; `1` = presence detected (moving, micro-moving, **or stationary** — this sensor claims to detect a motionless/sleeping person, unlike simple PIR) |
| par2/par3/par4 | Reserved placeholders, blank when idle (e.g. `$JYBSS,1,,,*`) |

Firmware (`prop_aux_radar.c`) reads only byte 7 of each line (right after `"$JYBSS,"`) as par1
— correct and sufficient; par2–4 aren't needed.

## 5. Integration gotchas specific to this firmware

- **Wiring**: UART1, TX=GPIO34→sensor RX, RX=GPIO33←sensor TX, connector **J10** — differs from
  the README's Arduino/FireBeetle pin-table examples (those are for other host boards).
- **Sensor is silent until commanded** — firmware sends `sensorStart` at boot (doesn't rely on
  `sensorCfgStart 1` persisting).
- **Boot sequence actually sent**: after a 700ms settle delay, `"\rsensorStop\r"`, then 350ms
  later `"\rsensorStart\r"`. The **leading `\r`** is a deliberate, empirically-learned hack to
  absorb a first-byte glitch on the sensor's CLI — not documented anywhere in vendor sources.
  Since no `detRangeCfg`/`outputLatency`/`saveCfg` is ever sent, the "must saveCfg to persist"
  rule is never actually exercised by this codebase — `sensorStop` here just clears prior
  running state, it's not real reconfiguration.
- **Self-healing**: if the stream goes silent for 5000ms, the driver assumes the sensor
  self-reset and automatically re-issues `sensorStart` (`sen0395_kick()`), resetting its own
  offline-detection timer — no need to resend `sensorStop` first.
- No `detRangeCfg`/`outputLatency` calls are ever sent — this firmware runs entirely on the
  sensor's factory-default 0–3m range and 2.5s/10s latencies. Tighter range gating (e.g. to
  reduce false triggers outside a prop's intended detection zone) is an unexploited capability;
  would need `sensorStop` → `detRangeCfg` → `saveCfg` → `sensorStart`, respecting the ≥1000ms
  inter-command gap.
- Two aux-radar UARTs run as independent FreeRTOS tasks pinned to core 1, each degrading
  independently to `AUX_OFFLINE` after 5s of silence — this driver is more resilient (active
  re-kick) than the Seeed MR24HPC1 driver (which just logs a warning and waits for the next poll).
